# Self-Intro 비공개 베타테스터 가이드

- 최종 갱신: 2026-08-22
- 대상: Self-Intro 초대 메일 또는 초대 코드를 받은 사용자
- 문의 시 전달할 정보: 발생 시각, 현재 URL, 화면 캡처, 수행한 단계
- 전체 제품 구조: [제품 기능 지도](../product/feature-map.md)

## 1. 비공개 베타의 의미

Self-Intro는 경력·프로젝트·학습 근거를 한 Workspace에서 관리하고 공개 이력과 지원별 이력서로
발행하는 서비스다. 현재는 개인정보와 Workspace 데이터 격리를 검증하는 단계이므로 누구나 가입하는
공개 서비스가 아니라 운영자가 초대한 사용자만 가입할 수 있다.

초대 코드는 결제 코드나 추천인 코드가 아니다. 가입 가능 대상을 제한하고 잘못 공유된 가입 링크를
운영자가 폐기하기 위한 임시 접근 수단이다.

비공개 베타 기간에는 카드 등록, 구독 결제, AI point 구매와 추가 좌석 결제를 받지 않는다. 요금제
화면의 Free·Pro·Business는 정식 출시를 준비 중인 예정 혜택을 비교하기 위한 안내다. 베타 계정을
자동으로 유료 전환하지 않으며, 정식 출시 전 가격·결제일·환불 조건을 별도로 알리고 사용자의 동의를
다시 받는다.

외부 AI 기능을 베타에 포함하는 경우에는 호출 전에 처리 사업자, 전송되는 정보, 처리 목적, 처리
국가·보유기간과 동의 거부 시 영향을 별도로 안내한다. 이 정보가 확정되지 않은 AI 기능은 베타에서
제공하지 않는다. 베타의 무료 AI 사용은 구매 point가 아니며 유료 전환 뒤 잔액으로 승계되지 않는다.

## 2. 초대를 받는 방법

운영자는 다음 두 종류 중 하나를 발급한다.

| 유형      | 사용 대상                | 특징                                      |
| --------- | ------------------------ | ----------------------------------------- |
| 개인 초대 | 지정된 이메일 소유자 1명 | 해당 이메일로만 가입할 수 있는 1회용 초대 |
| 공용 초대 | 제한된 테스트 그룹       | 운영자가 정한 횟수와 만료시각 안에서 사용 |

개인 초대는 이메일의 가입 링크로 전달된다. 공용 초대는 운영자가 신뢰할 수 있는 채널에서 코드 또는
링크를 전달한다. 전달받은 링크와 코드를 다른 사람에게 공유하지 않는다.

## 3. 가입 절차

1. 초대 메일의 링크를 열거나 `https://서비스주소/signup`에서 초대 코드를 입력한다.
2. 개인 초대라면 초대를 받은 이메일과 같은 이메일을 입력한다.
3. 닉네임과 비밀번호를 입력하고 필수 약관에 동의한다.
4. `확인 메일 받기`를 누른다.
5. 두 번째 이메일의 확인 링크를 열어 이메일 소유권을 확인한다.
6. 로그인한 뒤 첫 Workspace 이름을 정한다.
7. 비공개 Workspace 관리 화면에 진입한다.

Workspace가 공개된 뒤 방문자는 같은 slug 아래에서 다음 메뉴를 사용한다.

- `프로필`: `/workspace/{slug}`
- `경험`: `/workspace/{slug}/experience`
- `학습`: `/workspace/{slug}/study`
- `개발자 온톨로지`: `/workspace/{slug}/ontology`

로그인한 사용자가 해당 Workspace의 멤버일 때만 공개 화면 우측에 `Workspace 관리` 버튼이 보인다.
`OWNER`, `ADMIN`, `EDITOR`는 권한 범위 안에서 편집할 수 있고 `VIEWER`는 관리 화면을 읽기 전용으로
확인한다. 다른 Workspace 방문자에게는 이 버튼이 노출되지 않는다.
관리 버튼은 `/workspace/{slug}/manage`로 이동한다. 모든 멤버가 같은 관리 셸을 사용하지만 플랫폼
초대·통계·후원·Grafana·ArgoCD 메뉴는 플랫폼 운영자에게만 표시된다. Workspace 인가가 끝나지 않은
기존 편집 메뉴는 데이터 격리가 완료될 때까지 일반 베타테스터에게 표시하지 않는다.
관리 메뉴는 다음 기준으로 읽는다.

- `Workspace 설정`: 현재 Workspace의 기본 설정, 멤버·권한, 공개 페이지 통계
- `홈`: 현재 Workspace의 원본 기록·기술·역량·지원 현황과 공개 revision 상태를 요약하며, 플랫폼 전체
  통계나 다른 Workspace 수치를 섞지 않음
- `내 기록`: 경력·프로젝트, 학습 기록, 기술 스택, 학습 자료. 저장해도 자동 공개되지 않음
- `공개 페이지`: 공개본·버전, 프로필·연락처, 대표 역량, 대표 프로젝트, 포트폴리오, 경험 온톨로지.
  `공개본·버전`에서 새 버전을 발행해야 방문자에게 반영
- `지원·출력`: 지원 현황, 이력서·PDF 템플릿. 공개 메인페이지와 별도

사이드바 그룹 제목 옆 도움말 버튼을 누르거나 포인터를 올리면 현재 저장이 공개 페이지에 미치는 영향을
어두운 툴팁으로 확인할 수 있다. 목록 화면에는 자체 제목과 설명만 한 번 표시된다. 운영자 계정에는 위
메뉴 아래에 어두운 `플랫폼 운영자 전용` 블록 하나가 추가되지만, 일반 베타테스터에게는 렌더링되지
않는다.
일반 베타테스터도 자신의 Workspace에서 프로필, 이력·경력, 공부 정리, 기술 스택, 핵심 역량,
핵심 프로젝트 노출·순서와 포트폴리오 Case Study를 관리할 수 있다. 핵심 프로젝트에는 현재
Workspace에 등록한 프로젝트만 추가할 수 있고, 선택한 상세 경험과 공개 순서도 해당 Workspace에만
적용된다. 기술 스택은 플랫폼의 공통 기술 카탈로그에서 선택하되 숙련도·설명·핵심 여부는 각
Workspace에만 저장된다. 공부 정리 화면의 `공개 학습 카테고리`에서 공통 분류 중 공개 화면에 노출할
항목을 고른다. Workspace에 연결된 경력·학습·역량이 남은 기술은 먼저 연결을 해제해야 삭제할 수 있다.
포트폴리오는 자신의 Workspace 프로젝트만 선택할 수 있고, 다른 Workspace의 ID를 직접 입력해도
조회·수정하거나 근거로 연결할 수 없다. 학습 자료는 공통 catalog에서 선택하되 상태·우선순위·요약·
학습 노트·태그가 자신의 Workspace에만 저장된다. 일반 계정은 공통 공고를 선택해 자신의 지원 상태·메모·관심도·
상태 이력과 자기소개서 문항·답변을 관리할 수 있다. AI 자기소개서·어필 분석·보완 프로젝트도 현재
Workspace의 경력 근거만 사용하며 결과는 해당 지원 건에 귀속된다. PDF 초안·최종 제출 파일의 서버
경계도 Workspace 단위로 전환됐다. 일반 사용자는 PDF 템플릿 CRUD와 인쇄 미리보기를 사용할 수 있고,
플랫폼 Worker가 필요한 지원 공고·Portfolio AI revision 버튼만 표시되지 않는다.
이력·Study·핵심 역량 AI 초안은 현재 Workspace의 데이터만 사용하며 일반 Workspace 편집자에게
표시된다. 플랫폼 공용 데이터나 운영 설정을 바꾸는 AI 기능은 계속 플랫폼 운영자에게만 표시된다.
지원 공고 편집 화면의 `자동 매칭 다시 계산`은 현재 Workspace에 연결한 기술만 사용한다. 공고 원문은
모든 Workspace가 함께 쓰는 catalog지만 점수와 근거는 현재 Workspace 지원 건에만 저장되므로, 같은
공고를 저장한 다른 테스터의 점수에는 영향을 주지 않는다.
개발자 온톨로지의 상황·선택지·트레이드오프는 모든 Workspace가 읽는 공통 지식이다. 여기에 표시되는
학습 근거는 현재 Workspace의 Study만 연결할 수 있으며, 다른 테스터가 같은 상황에 연결한 Study는
내 관리 화면이나 공개 페이지에 나타나지 않는다.
Workspace `OWNER`와 `ADMIN`은 관리 화면의 `방문자 통계`에서 자기 공개 Workspace의 순 방문자와
조회 수만 확인할 수 있다. `EDITOR`와 `VIEWER`에게는 이 메뉴가 보이지 않는다. 기존 플랫폼 전체
방문 기록은 Workspace별로 신뢰성 있게 나눌 수 없어 이 기능 적용 시점부터 새로 집계되며, 플랫폼
운영 화면의 전체 방문자 통계와 숫자가 다를 수 있다.

관리 화면에서 콘텐츠를 `저장`하는 것은 초안 저장이다. 방문자에게 반영하려면
`공개 페이지 > 공개본·버전`에서 `첫 버전 발행` 또는 `새 버전 발행`을 눌러야 한다. 프로필,
공개 경력·프로젝트, 기술 스택, 대표 역량·프로젝트, 공개 학습 기록, 경험 온톨로지가 한 버전으로
묶인다. 포트폴리오 사례는 `포트폴리오`에서 사례별로 따로 발행한다. 첫 발행 전에는 비공개
Workspace가 404이고, 이미 공개 중이라면 방문자는 직전 발행본을 계속 본다. 발행과 공개 중지는
`OWNER`·`ADMIN`만 수행하며 `EDITOR`·`VIEWER`는 상태만 확인한다. `공개 중지` 후에도 초안과 과거
revision은 삭제되지 않으며 공개 URL만 404가 된다.

`공개 페이지 > 공개본·버전`의 `공개 초안 미리보기`는 현재 저장한 구성안을 보여주고, `현재 공개
페이지`는 방문자가 보고 있는 마지막 발행본을 보여준다. 첫 발행 전에도 초안 미리보기는 열리지만 공개
URL은 404가 정상이다. 발행 이력의 `현재 공개본` 표시와 상단의 최근 발행 버전이 일치해야 한다.

관리 화면 우측 상단의 계정 메뉴에서 현재 닉네임·로그인 이메일·Workspace 역할을 확인할 수 있다.
플랫폼 역할이 없다면 `일반 계정`으로 표시된다.
프로필 화면 안의 경력 카드나 관련 학습 링크를 눌러도 같은 `/workspace/{slug}` 경계 안에서
이동한다. 주소의 slug는 공개 라우팅 식별자일 뿐 비밀번호나 권한 증명이 아니며, `owner`, 이메일,
닉네임처럼 역할이나 개인정보를 드러내는 값은 사용하지 않는다.

Workspace `OWNER`와 `ADMIN`은 `Workspace 설정 > 기본 설정`의 `공개 주소 관리`에서 현재 비밀번호를 다시 확인한 뒤
canonical slug를 바꿀 수 있다. 영문 소문자·숫자·하이픈 3~60자를 사용한다. 변경 전 주소는 기존 공유
링크가 깨지지 않도록 alias로 남고 새 canonical 주소로 이동한다. 이전 주소를 안다고 해서 관리 권한이
생기지는 않으며, 다른 사용자는 계속 404로 처리된다. 주소 변경 뒤에는 브라우저가 새
`/workspace/{canonical-slug}`로 이동했는지 확인한다.

초대 링크는 `/signup#invite=...` 형식이다. `#` 뒤 코드는 서버 요청과 access log에 포함되지 않으며,
가입 화면에 자동 입력된 뒤 브라우저 주소에서도 즉시 제거된다. 링크 원문은 브라우저 기록, 캡처,
채팅에 남기지 않는다.

로컬 개발 환경에서는 실제 메일 서비스 대신 `http://localhost:8025`의 Mailpit에서 초대 메일과
이메일 확인 메일을 확인한다.

### 플랫폼 가입 초대와 Workspace 참여 초대 구분

두 메일은 용도가 다르다.

| 초대                  | 받는 시점                  | 결과                                 |
| --------------------- | -------------------------- | ------------------------------------ |
| 비공개 베타 가입 초대 | 플랫폼 계정이 없을 때      | `/signup`에서 계정을 만들 수 있음    |
| Workspace 참여 초대   | 가입·이메일 확인이 끝난 뒤 | 기존 계정이 특정 Workspace 멤버가 됨 |

Workspace 참여 초대는 `/workspace-invitations#invite=...` 링크로 전달된다. 링크를 열고 초대받은 이메일과
같은 계정으로 로그인한 뒤 `이 계정으로 수락`을 눌러야 권한이 생긴다. 참여하지 않으려면 `초대 거절`을
선택할 수 있으며, 거절 뒤 다시 참여하려면 Workspace 관리자에게 새 초대를 요청해야 한다. 다른 이메일 계정으로
로그인하면 Workspace 존재나 초대 상세를 노출하지 않고 거부한다. 로그인 화면을 거치는 동안 토큰은
현재 브라우저 탭의 `sessionStorage`에만 잠시 보관되고 수락·거절 후 제거된다. 초대는 처리 또는 만료 뒤
기본 30일 후 자동 삭제되며 삭제된 초대 이력은 복구되지 않는다.

자기 Workspace의 `OWNER`·`ADMIN`은 관리 화면의 `멤버·역할 관리`에서 협업자를 초대할 수 있다.
`ADMIN`은 `EDITOR`·`VIEWER`만 관리하며 `OWNER`·다른 `ADMIN`은 변경할 수 없다. 소유권 이전은 현재
`OWNER`가 비밀번호를 다시 확인한 뒤 명시적으로 실행하며, 이전 OWNER는 `ADMIN`이 된다. 플랫폼
운영자 역할만으로 다른 Workspace 멤버를 열람하거나 변경할 수는 없다.

### Workspace 이름 변경·탈퇴·폐쇄

- `OWNER`·`ADMIN`은 `Workspace 설정 > 기본 설정`에서 Workspace 표시 이름을 바꿀 수 있다. 공개 주소는 별도 설정이다.
- `ADMIN`·`EDITOR`·`VIEWER`는 Workspace에서 스스로 탈퇴할 수 있다. 작성한 콘텐츠는 Workspace에
  남으며 다시 참여하려면 새 초대가 필요하다.
- `OWNER`는 소유권을 이전하기 전에는 탈퇴할 수 없다.
- OWNER가 Workspace 이름을 다시 입력해 폐쇄하면 즉시 모든 멤버의 관리 접근과 공개 페이지가
  차단된다. 비공개 베타 기간에는 안전한 삭제 전파 검증을 위해 폐쇄 후 데이터가 유예 보관되며,
  폐쇄가 곧 물리 삭제 완료를 의미하지 않는다.
- 폐쇄 뒤 운영자 화면에는 이름이나 콘텐츠가 아니라 불투명 식별자와 저장소별 삭제 점검 상태만
  표시된다. Object Storage 점검도 파일명이나 경로가 아니라 공개·비공개 객체, 이전 version, 삭제 표식,
  미완료 업로드의 수와 용량만 보여준다.
  삭제 adapter가 있더라도 현재는 feature flag와 실행 경로가 모두 비활성화되어 자동 물리 삭제가
  수행되지 않는다. 즉시 삭제·복구가 필요하면 원문 개인정보를 일반 문의나 로그에 붙이지 말고
  운영자에게 별도 보안 요청으로 전달한다.

## 4. 자주 발생하는 상황

### 초대 링크가 유효하지 않다고 나오는 경우

- 개인 초대에 다른 이메일을 입력했는지 확인한다.
- 초대가 이미 사용됐거나 만료·폐기됐을 수 있다.
- 운영자에게 기존 링크 재사용이 아니라 **교체 발송**을 요청한다. 교체 발송 시 이전 링크는 폐기되고
  새로운 1회용 링크가 발급된다.

### 이메일 확인 메일이 오지 않는 경우

- 스팸 메일함과 입력한 이메일 주소를 확인한다.
- 가입 응답은 계정 존재 여부를 노출하지 않으므로 이미 가입한 이메일에도 같은 안내가 보일 수 있다.
- 확인 토큰은 기본 30분 동안 유효하고 한 번만 사용할 수 있다.

### Workspace 관리 기능이 적게 보이는 경우

Profile·이력·Study·기술 스택·핵심 역량·포트폴리오·학습 자료는 Workspace별로
작성할 수 있다. 지원 공고 관리, 자기소개서 AI, 어필 분석과 보완 프로젝트는 사용할 수 있다. PDF는
데이터·파일 격리를 완료해 일반 Workspace의 `PDF 템플릿 관리`에서 편집할 수 있다. Portfolio AI
revision처럼 플랫폼 운영 권한이 필요한 일부 버튼은 일반 계정에 표시하지 않는다. 메뉴가 적게 보이더라도
가입 실패가 아니다.

AI 학습 계획은 제품 범위에서 제거했다. 메뉴와 화면뿐 아니라 서버 API, 기존 계획 데이터와 테이블도
V235에서 함께 삭제하므로 비공개 베타 테스트 대상이 아니다. 이후 새 기획을 도입한다면 기존 계약을
재사용하지 않고 별도 기능으로 다시 설계한다.

### 첫 Workspace 생성에서 다시 로그인을 요청하는 경우

DB 복원이나 계정 상태 변경 전의 로그인 세션이 브라우저에 남아 있으면 보안을 위해 기존 세션을
무효화한다. 로그인 화면으로 이동하면 초대 가입 때 만든 이메일과 비밀번호로 다시 로그인한 뒤
`/onboarding/workspace`에서 같은 Workspace 이름으로 다시 생성한다. 생성 요청이 실패한 경우에는
Workspace가 일부만 만들어지지 않도록 전체 트랜잭션이 롤백된다.

  버튼으로 데이터를 바꿀 수 없는가

- 공통 기술을 추가한 뒤 Workspace별 설명·숙련도만 자기 화면에 저장되는가
- 같은 공고를 두 Workspace에 저장하고 자동 매칭을 실행해도 점수·근거가 서로 덮어쓰이지 않는가
- 같은 온톨로지 상황에 서로 다른 Workspace Study를 연결해도 공개 근거가 서로 섞이지 않는가
- 공개 학습 카테고리 선택이 자기 Workspace의 학습 화면에만 반영되는가
- 비공개 Workspace를 로그아웃 상태에서 열면 `404`가 나오는가
- 첫 발행 후 공개 페이지가 열리고, 초안을 수정해도 재발행 전에는 기존 공개본이 유지되는가
- 재발행 후 새 내용이 반영되고 공개 중지 후 다시 `404`가 되는가
- 다른 사용자의 Workspace 정보가 화면이나 API 응답에 섞이지 않는가
- 프로필의 경력·학습 링크를 눌렀을 때 주소가 같은 Workspace slug 아래에 유지되는가
- 공개 주소 변경 후 새 주소로 이동하고 이전 공개 주소도 새 canonical URL로 연결되는가
- 다른 계정이 이전 slug로 관리 API에 접근해도 404로 차단되는가
- 자신의 Workspace에서는 `Workspace 관리` 버튼이 보이고, 다른 사용자의 Workspace에서는 숨겨지는가

- `ADMIN`이 다른 `ADMIN`·`OWNER` 역할을 변경하거나 제거할 수 없는가
- 소유권 이전 뒤 새 OWNER와 이전 OWNER(ADMIN)의 권한이 즉시 반영되는가

## 6. 운영자와 베타테스터 역할의 차이

- 베타테스터의 `OWNER`는 자신의 Workspace를 관리하는 역할이다.
- 플랫폼 운영자의 `PLATFORM_OWNER` 또는 `PLATFORM_OPERATOR`는 초대와 플랫폼을 운영하는 역할이다.
- Workspace `OWNER`라고 해서 `/ops`에 접근할 수 없다.
- 플랫폼 운영자라고 해서 Membership 없이 다른 사용자의 Workspace 개인정보를 열람할 수 없다.

한 사람이 두 역할을 함께 테스트하더라도 화면과 권한은 이 경계를 기준으로 동작한다.

일반 베타테스터에게는 결제·AI point 구매·내 AI API 키 연결 기능이 제공되지 않는다. 운영 검증을 위해 지정한 하나의
Workspace에서는 `PLATFORM_OWNER`가 함께 확인된 경우에만 Toss 테스트 MID와 내 AI API 키를 이용한 외부 호출이 열린다.
이는 베타 혜택이나 유료 전환이 아니라 운영자 전용 샌드박스이며, 실제 청구·자동 유료 전환은 발생하지
않는다.

운영자는 베타테스터에게 수동 교차 접근 검증을 요청하기 전에 로컬 Compose에서
`./scripts/e2e/workspace-isolation-compose.sh`를 실행할 수 있다. 이 자동 검증은 임시 일반 사용자와
Workspace만 사용하고 종료 시 정리하며, 베타테스터의 실제 계정이나 콘텐츠를 테스트 fixture로 사용하지
않는다.

플랫폼 운영자 MFA 설정 키와 QR 코드는 베타 초대 코드가 아니다. 베타테스터에게 전달하거나 테스트
문제 제보 화면에 포함하지 않는다. 베타테스터는 운영자 MFA를 등록할 필요가 없다.

## 7. 운영자와 테스터를 함께 수행하는 권장 방법

1. 평소 브라우저에서는 플랫폼 운영자 계정으로 로그인해 `/ops`에서 본인과 다른 이메일을 대상으로 한
   개인 초대를 발급한다.
2. 시크릿 창 또는 별도 브라우저 프로필에서 초대 메일을 열어 베타테스터 계정을 가입한다.
3. 테스터 계정으로 만든 Workspace에서는 자신의 관리 화면과 공개 여부만 확인한다.
4. 다시 운영자 창으로 돌아와 초대의 `사용 완료` 상태와 사용 횟수를 확인한다.

같은 이메일·같은 로그인 세션으로 두 역할을 흉내 내면 세션과 권한 문제를 구분하기 어렵다. 실제
베타테스터 가입 흐름은 별도 이메일과 분리된 브라우저 세션으로 검증한다.

같은 브라우저 프로필의 일반 탭은 로그인 쿠키 하나를 공유한다. 한 탭에서 다른 계정으로 로그인하거나
로그아웃하면 나머지 탭도 계정 변경을 감지해 메인 화면으로 이동하고, 이전 계정의 query cache와 저장 전
미리보기 초안을 폐기한다. 운영자와 베타테스터를 동시에 확인하려면 반드시 시크릿 창, 별도 브라우저
프로필 또는 다른 브라우저를 사용한다.

## 8. 로컬 사용자 인수 테스트 시작점

2026-08-14 자동 gate 기준으로 backend 전체 test, frontend 포맷·TypeScript·production build,
ESLint error 0·warning 29, Compose 9단계 교차 Workspace E2E와 비로그인 브라우저 smoke test가 통과했다.
E2E는 별도 사용자·Workspace·cookie를 사용해 가입 이후의 로그인, 발행·rollback, slug, Profile·Study·
Skill·지원·Membership·폐쇄 경계를 검증하며 종료 전 Experience·Study 삭제 이벤트가 Oracle Vector까지
반영돼 fixture 잔여가 0인지 확인한다. 현재는 운영 배포 전 **로컬에서 직접 접속해 사용자 흐름을 확인하는
단계**다.

추가로 `./scripts/e2e/registration-onboarding-compose.sh`가 로컬 전용 개인 초대부터 실제 Mailpit 확인 메일,
확인 전 로그인 차단, 단일 사용 이메일 확인, 일반 사용자 로그인, 첫 비공개 Workspace, Profile 저장과 첫
공개 발행까지 통과했다. 자동 UAT의 임시 계정·Workspace·초대는 종료 후 모두 삭제된다. 자동 검증은 API와
프런트 route의 연결을 증명하지만 사람이 보는 문구·입력 편의·이동 동선까지 대신하지 않으므로 아래의
별도 브라우저 UAT는 유지한다.

운영자 관점은 평소 브라우저에서 다음 순서로 확인한다.

1. `http://localhost:3000/login`에서 플랫폼 운영자 계정의 아이디·비밀번호를 먼저 확인한 뒤, 별도
   2단계 화면에서 인증 앱의 6자리 MFA 코드를 입력한다. MFA 완료 전에는 로그인 세션이 발급되지 않는다.
2. 자기 `/workspace/{slug}/manage`에서 현재 로그인 계정·플랫폼 역할·Workspace 역할이 맞는지 확인한다.
3. `/ops` 권한 메뉴에서 비공개 베타 개인 초대를 발급하고 Mailpit `http://localhost:8025`에서 메일을
   확인한다. 초대 코드와 MFA 설정 키는 화면 캡처에 포함하지 않는다.
4. 관리 셸의 `플랫폼 운영 > Vector 정합성 점검`에서 `정합성 점검 실행`을 누르고 Experience·Study의
   MySQL 원본, Vector namespace, 고아 namespace와 누락 namespace 수를 확인한다. 점검 자체는 read-only며
   자동 수정하지 않는다. 고아 namespace가 있으면 정확한 삭제 수를 확인하고 최근 비밀번호 재확인을
   완료한 뒤 `고아 Vector만 삭제`를 실행할 수 있다. 이 작업은 MySQL 원본과 현재 원본에 연결된 Vector를
   변경하지 않고 외부 임베딩 API도 호출하지 않는다. 전체 백필·누락 Vector 생성·DLQ purge는 별도 운영
   결정 없이 실행하지 않는다. 누락 Vector를 복구할 때는 별도 빨간 영역에 표시된 누락 건수와 제목·본문
   청크의 NVIDIA API 전송을 확인하고 재인증한 경우에만 실행한다.
5. 2026-08-12 과거 E2E cleanup에서 남았던 고아 Experience·Study namespace 각각 2개는 운영자가 정확한
   범위를 확인하고 최근 비밀번호 재확인을 마친 뒤 전용 UI로 삭제했다. 이어 실행한 read-only 점검의
   기준선은 Experience 17/17, Study 70/70, 양쪽 고아·누락 0이다. 이후 점검에서 이 값이 달라지면 자동
   삭제·전체 백필을 실행하지 말고 원인과 영향 Workspace부터 확인한다.

베타테스터 관점은 시크릿 창 또는 별도 브라우저 프로필에서 다음 순서로 확인한다.

1. Mailpit의 개인 초대 링크로 `/signup#invite=...`를 열어 가입한다.
2. 확인 메일을 처리한 뒤 로그인하고 첫 비공개 Workspace를 만든다.
3. Profile·경력·Study를 각각 한 건 저장한 뒤 새로고침해 자기 Workspace에만 남는지 확인한다.
4. 공개 발행 전에는 `/workspace/{slug}`가 열리지 않고, 첫 발행 뒤 공개되는지 확인한다.
5. 초안을 수정했을 때 재발행 전 공개본이 유지되고 재발행 뒤에만 바뀌는지 확인한다.
   같은 화면에서 `공개 초안 미리보기`와 `현재 공개 페이지`를 각각 열어 두 상태가 의도대로 다른지도
   확인한다.
6. 로그아웃 상태에서 공개 Profile·경험·학습을 이동하고 관리 주소는 로그인 화면으로 전환되는지
   확인한다.
7. 이력, Study, 핵심 역량에서 AI 초안을 각각 한 번 열고 후보 목록에 다른 Workspace 콘텐츠가 없는지,
   생성 결과가 현재 작성 폼에만 반영되는지 확인한다. 실제 실행은 외부 AI provider 사용량이 발생할 수
   있으므로 로컬 설정과 사용 의사를 먼저 확인한다.
8. `PDF 템플릿 관리`에서 템플릿 하나를 만들고 새로고침 후 다시 보이는지 확인한 뒤, 복제·수정·삭제와
   인쇄 미리보기까지 확인한다. 미리보기에서 기존 항목을 다른 항목의 왼쪽·오른쪽 drop 안내선으로
   끌어 두 항목이 같은 Row의 Column으로 배치되는지 확인한다. Row 위에 마우스를 올려 2열 폭·간격을 바꾸고,
   `여백`에서 상하좌우 5~30mm를 조절한다. 템플릿을 저장·다시 열어 배치와 여백이 유지되는지도
   확인한다. 빨간 `열 높이 초과` 경고가 보이면 항목을 반대 열이나 다음 페이지로 이동한 뒤 인쇄한다.
   Workspace 계약을 아직
   만들지 않은 AI revision 버튼이 없는 것은 정상이다.
9. `지원 현황`에서 `공통 공고 찾기`로 공고 하나를 자기 Workspace에 추가한다. `내 지원 관리`의
   리스트·보드·캘린더를 전환하고 상태·메모·관심도·자기소개서가 저장되는지 확인한다. 수집·원본 수정·
   공고 삭제 같은 플랫폼 운영 메뉴가 보이지 않는 것이 정상이며, 공통 공고를 추가해도 다른 사용자의
   지원 상태나 메모는 보여서는 안 된다. 리스트의 상태 필터와 회사·직무·지역 검색이 보드와 캘린더에도
   동일하게 적용되고, 마감일이 없는 공고는 캘린더 날짜 칸에 임의로 표시되지 않는지도 확인한다.
   `공통 공고 찾기` 카드의 `원본 보기`가 새 탭에서 원본 채용 사이트를 열고, 공통 목록에는 상세 본문·
   지원 자격·우대 사항 대신 회사·직무·지역·고용형태·마감일과 출처만 보이는 것이 정상이다. 지원 전에는
   반드시 원본에서 공고가 아직 유효한지 다시 확인한다.

현재 로컬 기준 공개 예시 주소는 `http://localhost:3000/workspace/{slug}`이며, 관리 주소는
`http://localhost:3000/workspace/{slug}/manage`다. `{slug}`는 로그인 후 계정 메뉴에 표시되는 자기
Workspace의 불투명 공개 식별자로 바꾼다.
