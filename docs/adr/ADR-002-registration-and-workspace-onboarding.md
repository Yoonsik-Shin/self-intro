# ADR-002: 회원가입과 첫 Workspace 온보딩 계약

- 상태: Accepted
- 기준일: 2026-08-10
- 관련 문서: [ADR-001](./ADR-001-saas-security-multitenancy.md)

## 배경

사용자 계정과 Workspace는 수명이 다르다. 한 사용자가 여러 Workspace에 참여할 수 있고,
Workspace에는 여러 멤버가 참여할 수 있다. 로그인 식별자, 사용자 표시 이름, Workspace 이름,
공개 URL slug를 하나의 "아이디"로 취급하면 이름 변경과 공개 URL 변경, 초대, 계정 복구가 서로
결합된다.

기존 bootstrap 운영자의 `app_user.login_id`는 호환 컬럼으로 남아 있다. 역할을 노출하던 과도기
Workspace slug는 V196에서 무작위 provisional slug로 교체했고 이전 주소는 alias로 보존하지 않는다.

## 결정

회원가입과 첫 Workspace 생성을 두 단계로 분리한다.

### 1단계: 계정 생성

필수 입력:

| 필드                   | 용도                           | 공개 여부                        |
| ---------------------- | ------------------------------ | -------------------------------- |
| 이메일                 | 로그인, 소유권 확인, 계정 복구 | 비공개                           |
| 비밀번호               | 로컬 인증                      | 저장하지 않고 단방향 해시만 저장 |
| 닉네임(`display_name`) | 제품 내부에서 사용자를 구분    | 기본 비공개                      |
| 이용약관 동의          | 서비스 이용 계약               | 비공개 감사 정보                 |
| 개인정보 처리 동의     | 필수 개인정보 처리 근거        | 비공개 감사 정보                 |

선택 입력:

| 필드             | 원칙                             |
| ---------------- | -------------------------------- |
| 마케팅 수신 동의 | 필수 동의와 분리하고 기본 미동의 |

가입 단계에서 받지 않는 정보:

- 별도 로그인 아이디
- 전화번호, 주소, 생년월일, 성별
- 실명 및 실명 인증 정보
- 직무, 경력 연차, 기술 스택
- GitHub, 블로그, 이력서 파일
- Workspace slug

이메일은 로그인 표시값과 비교용 canonical 값을 분리해 저장한다. 소유권 확인 전 계정은
`PENDING_VERIFICATION`이며 Workspace 데이터 작성과 공개 발행을 허용하지 않는다. 확인 토큰은
단일 사용·유효기간 제한·안전한 난수로 발급하고 토큰 원문과 전체 이메일 주소를 로그에 남기지 않는다.

비밀번호는 긴 passphrase와 비밀번호 관리자를 허용한다. 문자 종류 조합 규칙이나 주기적 변경을
강제하지 않고, 알려진 취약 비밀번호 차단과 가입·로그인 rate limit을 적용한다.

### 2단계: 첫 Workspace 온보딩

이메일 확인 후 다음 값을 받는다.

| 필드                | 처리 방식                                              |
| ------------------- | ------------------------------------------------------ |
| Workspace 이름      | 화면에 표시되는 이름. 기본 제안값을 제공하고 수정 가능 |
| Workspace 임시 slug | 시스템이 개인정보와 무관한 임의 값으로 생성            |

Workspace 생성 시에는 읽기 쉬운 공개 slug 선택을 강제하지 않는다. 내부 `workspace_id`와 별도로 UUID v4
기반의 불변 `public_key`와 `w-{20자 난수}` 형식의 provisional slug를 생성하고, Workspace는 비공개
상태로 시작한다. provisional slug는 `/workspace/{slug}/manage` 관리 라우팅에 사용하지만 공개 조회를
허용한다는 뜻은 아니다. 사용자가 공개 발행을 시작할 때 다음
두 방식 중 하나를 선택한다.

1. 읽기 쉬운 공개 slug를 직접 선택한다. 예: `yoonsik-shin`
2. 개인정보 노출을 원하지 않으면 시스템이 생성한 provisional slug를 그대로 공개 주소로 사용한다.

공개 slug 규칙:

- 소문자 영문, 숫자, 하이픈만 허용
- 3~60자
- 전체 Workspace에서 유일
- `admin`, `ops`, `api`, `login`, `signup`, `support`, `demo` 등 예약어 금지
- 이메일이나 전화번호처럼 개인정보가 포함된 값은 사용하지 않도록 안내
- 계정 이메일, 실명, 닉네임으로부터 자동 생성하지 않음
- 공개 발행 전에는 자유롭게 선택·변경 가능
- 공개 발행 후 변경은 재인증을 요구하고 이전 slug redirect alias와 감사 기록을 남김

`public_key`와 `slug`는 별개다. `public_key`는 DB 외부 이벤트·객체 저장소·감사 로그에서 Workspace를
안정적으로 가리키는 무의미한 불변 식별자다. `slug`는 사람이 공유하는 URL alias이며 변경될 수 있다.
접근 권한은 어느 값의 추측 난이도에도 의존하지 않고 Membership과 공개 발행 상태로 판단한다.

Workspace 생성 결과:

1. `Workspace`를 기본 비공개 상태로 생성한다.
2. 가입 사용자를 `OWNER` Membership으로 연결한다.
3. 빈 Profile과 온보딩 진행 상태를 생성한다.
4. 사용자가 명시적으로 발행하기 전에는 `/workspace/{slug}` 공개 응답을 제공하지 않는다.

## 이름과 실명 인증 모델

이름은 다음 세 책임으로 분리한다.

| 값                  | 소유 범위         | 용도                                  | 공개 여부               |
| ------------------- | ----------------- | ------------------------------------- | ----------------------- |
| 닉네임/표시 이름    | 사용자 계정       | 멤버 목록, 초대, 협업 UI              | 기본 비공개             |
| 인증 실명           | 별도 인증 정보    | 향후 실명 인증이 필요한 기능          | 항상 비공개             |
| Workspace 공개 이름 | Workspace/Profile | 공개 이력과 문서의 작성자·브랜드 표시 | 사용자가 발행할 때 선택 |

`app_user.display_name`은 실명이 아니라 변경 가능한 닉네임으로 정의한다. 인증 실명을 같은 컬럼에
덮어쓰지 않는다. 향후 실명 인증 provider를 붙일 때 `verified_identity`와 같은 별도 보안 경계에
provider reference, 인증 상태, 인증 시각, 필요한 최소 속성만 저장한다. 원문 실명이 반드시 필요하지
않다면 provider의 검증 결과와 내부 연결 식별자만 저장한다. 필요한 경우에도 암호화·접근 감사·보존기간·
삭제 전파를 별도로 적용하며 공개 Profile로 자동 복사하지 않는다.

Workspace 공개 이름은 계정 닉네임 및 인증 실명과 독립적이다. 개인은 실명이나 필명을 선택할 수 있고,
팀 Workspace는 팀·브랜드명을 사용할 수 있다.

### 가입 개방 정책

첫 운영 단계는 초대 코드가 필요한 비공개 베타로 시작한다. 개인정보 격리, 이메일 확인, 비밀번호
재설정, 탈퇴·삭제 전파, 사용량 제한, 두 사용자·두 Workspace E2E가 검증된 후 공개 가입으로 전환한다.
초대 코드는 계정이나 Workspace 식별자가 아니며 만료·사용 횟수·발급자를 기록한다.

## 계정과 Workspace의 식별자

- 인증 주체: 내부 `user_id`
- 로그인 표시값: 이메일
- 사용자 표시: 변경 가능한 닉네임 `display_name`
- Workspace 보안 경계: 내부 `workspace_id`와 UUID v4 `public_key`
- Workspace 공개 표시: Workspace/Profile의 공개 이름
- Workspace 공개 주소: 발행 시 사용자가 선택하거나 시스템이 무작위 생성한 `workspace.slug`
- 실명 인증: 계정과 1:1로 연결되는 별도 `verified_identity`

`login_id`를 공개 회원가입 필드로 노출하지 않는다. 기존 bootstrap 로그인을 위한 호환 컬럼으로만
유지한 뒤 이메일 로그인 전환 migration에서 역할을 축소한다.

## 가입 흐름

```text
초대 코드 확인
  → 이메일·비밀번호·표시 이름·필수 동의
  → 이메일 소유권 확인
  → Workspace 이름 설정
  → UUID public_key와 provisional slug를 가진 비공개 Workspace 생성 + OWNER Membership
  → 경력 데이터 온보딩
  → 공개 발행 시 slug 선택 또는 무작위 slug 유지
  → 사용자의 명시적 공개 발행
```

## 구현 전 결정이 필요한 항목

- 실제 서비스에 사용할 이메일 발송 provider
- 이메일 확인 토큰 유효시간
- 서비스명에 맞춘 기본 Workspace 이름 제안 문구
- 기존 bootstrap Workspace의 공개 slug는 V196에서 개인정보·역할과 무관한 난수로 전환 완료
